Executive conclusion

有明确机会，但不是再做一个 Web Search 供应商

CowAgent 已完整接入 Bocha、Qianfan、Zhipu、LinkAI 四家搜索后端。Lexmount 当前没有搜索 API，因此不应在 web_search 中伪装成第五家搜索服务。合适的产品位置是：以 Moli 提供本地低资源浏览器，以 Lexmount WebFetch 提供动态页面提取，以 Lexmount Cloud Browser 提供可托管的 Chromium / Moli 生产运行时。

最小可行策略是“本地免费入口 + 云端双内核生产升级”：DOM 驱动任务优先试用本地 Moli；兼容性敏感任务继续使用 Chromium；并发、代理、会话管理、可观测与人工接管需求升级到 Lexmount Cloud Browser。这个路径成立，但在缺少客户分布数据时，不应宣称 Moli 会成为“大部分客户”的默认选择。

01 · Current state

CowAgent 的三层 Web 能力现状

CowAgent 将联网能力拆成搜索发现、页面读取和浏览器交互。Lexmount 的价值应沿着这三个边界接入，避免复制已经存在的能力。

Web Search：四家均已集成，不是候选名单

供应商CowAgent 当前调用凭证与界面结论
BochaPOST api.bochaai.com/v1/web-search独立 bocha_api_key；Web 控制台有专门配置已实现
Qianfan/ai_search/web_search复用千帆模型供应商 API Key已实现
Zhipu/web_search复用智谱模型供应商 API Key已实现
LinkAI/v1/plugin/execute，插件码 web-search复用 LinkAI 模型供应商 API Key已实现

实现不止存在于文档：后端分别发送真实 HTTP 请求，统一为 {query, backend, total, count, results}；控制台能选择 auto 或固定供应商；无任何有效 Key 时，web_search 不注册；配置两家以上且为自动策略时，模型才会看到逐次选择 provider 的参数。

当前缺口：主干没有独立的 Web Search 单元测试文件。四家实现是明确的，但真实 API 的字段漂移、限流和错误返回仍依赖凭证环境验证。Lexmount 可以在商业上为这些供应商提供底层浏览器基础设施；这属于 B2B 供给关系，不等于 CowAgent 中新增 Lexmount Search Provider。

Web Fetch 与 Browser：Lexmount 的直接进入点

Web Fetch

当前工具适合 HTTP 可直接读取的内容，也处理 PDF、Office 等文档。遇到 JavaScript 渲染、反爬、登录态和需要动作后才出现的正文时，需要升级到浏览器。

Browser

当前由 Playwright 驱动，支持内置浏览器、系统 Chrome/Edge 与外部 CDP Endpoint；动作包括导航、快照、点击、填写、选择、滚动、截图、脚本执行、前进后退等。外部 CDP 是 Moli 和 Lexmount Cloud 的现成协议接缝。

02 · Product position

Lexmount 应提供一条递进式运行路径

本地 Moli
免费安装；单进程、低内存；适合 DOM / 可访问性树驱动任务和本地应用。
→
Cloud Moli
低资源内核的托管版本；面向高并发、结构化网页自动化。
↔
Cloud Chromium
面向像素、Canvas/WebGL、媒体、复杂下载和高兼容工作负载。
产品主要用户价值适合不应承诺
本地 Moli零云成本试用；资源占用低；可访问 localhost / 内网网页读取、表单、后台系统、批量 DOM 操作当前不作为默认 Provider；不承诺像素级视觉一致
Lexmount WebFetch把页面渲染与正文提取托管化，降低 Agent token 与重试开销JS 页面、批量内容读取、浏览器前的轻量升级不能替代搜索索引或搜索排序
Cloud Moli低资源高密度会话、统一生命周期、代理与远程观察并发 Agent、结构优先自动化、服务端部署Chromium 的全部图形与持久化能力
Cloud Chromium完整浏览器兼容性、复杂网页、企业运行控制视觉任务、媒体、下载、录制、复杂登录流程与 Moli 相同的单位资源成本

Lexmount Cloud 同时提供 Chromium 和 Moli 是关键优势：用户可在同一供应商下按工作负载选内核。不过两种内核能力并不等价；公开文档显示，Moli 会话不支持 Contexts、持久录制与下载持久化，应在 CowAgent 配置界面明确展示。

03 · Concrete usage

三个真实用法：从本地测试到生产运行

例一：本地 Moli 直接复用 CowAgent 现有 Browser 动作

开发者希望让 CowAgent 操作本地管理台，不希望上传登录态，也不想启动多进程 Chromium。Moli 在本机提供 CDP，CowAgent 不需要修改动作协议：

# 安装 Moli 后启动本地 CDP 服务
moli serve --layout --host 127.0.0.1 --port 9222

# CowAgent config.json
{
  "tools": {
    "browser": {
      "cdp_endpoint": "http://127.0.0.1:9222"
    }
  }
}

随后用户可提出：“打开 http://127.0.0.1:3000/admin，筛选失败任务，导出错误摘要。”导航、snapshot、fill、click、get_text 等仍由 CowAgent 原工具完成。--layout 对依赖坐标或可见性判断的页面更稳妥。

例二：搜索 → 提取 → 浏览器的分层升级

用户：找出三家厂商最新价格并比较退款条款。

1. web_search(provider="bocha") 发现候选 URL
2. web_fetch(provider="lexmount") 提取普通/JS 渲染页面正文
3. 仅当价格需选规格、同意 Cookie 或登录后出现时：
   browser(engine="lexmount", kernel="moli" | "chromium")

搜索负责“找到哪里”，WebFetch 负责“低成本读出来”，Browser 负责“执行动作后取得结果”。让所有 URL 一开始就启动浏览器会增加成本；只做静态 fetch 又会漏掉动态内容。

例三：云端生产会话必须由 CowAgent 管理生命周期

# LEXMOUNT_API_KEY 与 LEXMOUNT_PROJECT_ID 由环境变量提供
from lexmount import Lexmount

client = Lexmount()
with client.sessions.create(
    browser_mode="light",         # Moli；Chromium 使用 "normal"
    enable_lightmount_layout=True
) as session:
    await browser_service.connect_cdp(session.connect_url)
    # CowAgent 继续执行 navigate / snapshot / click / fill ...
# 退出 with 时 SDK 关闭 session

静态填写 cdp_endpoint 可以做 PoC，但不够支撑正式云集成：生产版本必须创建会话、连接、暴露只读 Inspect/View 地址、在超时或任务结束时回收，并在日志中隐藏含凭证的 WebSocket URL。

04 · Compatibility evidence

Moli 作为 Browser Provider 应如何选择？

本报告在隔离目录下载 Moli 1.0.6，使用 CowAgent 当前桌面依赖的 Playwright 1.52.0，并直接加载 CowAgent 的 BrowserService 连接本地 Moli CDP。测试页面覆盖文本框、下拉框、按钮、导航和长页面。

15 / 15 通过

navigate、snapshot、ref 填写/点击、select、get_text、evaluate、scroll、wait、screenshot、selector 点击、跳转、back、forward、press。

3.06 秒

合入 Provider 后的完整 BrowserTool 动作合同测试耗时；生成有效 PNG，工具关闭后 Moli 进程自动回收（单次本机样本，不作跨平台基准）。

不是全兼容证明

测试未覆盖复杂 SSO、Canvas/WebGL、视频、下载持久化、反自动化站点和长时间多页会话。

Moli 公布的 agent 样本中，峰值 PSS 为 102.46 MiB，Chromium 为 348.82 MiB；公开混合抓取样本的中位 RSS 为 73 MiB 对 773 MiB。但更广的 1,308 项 Lexbench 中，Moli 可比通过率为 81.88%，Chrome/Chromium 基线为 99.85%。经 Moli 官方确认，该 Lexbench 任务集上 Chrome 与 Chromium 的结果完全一致。数据支持“速度与资源成本优先时推荐 Moli”，但在成功率接近或对齐前，不支持把 Moli 设为默认 Provider。

工作负载推荐内核理由
DOM 读取、表单、后台、批量网页操作，且速度/成本优先推荐 Moli协议已实测兼容，资源优势可转化为并发密度
本地网站、内网系统、隐私敏感登录态本地 Moli / Chromium云端默认无法访问用户 localhost / LAN；按页面兼容性选择
Canvas、WebGL、视频、像素级截图、复杂扩展ChromiumMoli 的轻量渲染模型不是完整 GUI Chromium
生产高并发且页面结构可控Cloud Moli低资源内核 + 托管会话与代理能力
未知网站或最高兼容性优先Cloud Chromium避免因内核差异导致隐性失败
产品结论：Moli 与 Chromium 是并列的 Browser Provider。“本地 Moli 免费试用 → Lexmount Cloud 生产升级”是合理漏斗；首版让用户显式选择，并在速度/成本优先场景标记 Moli 为推荐项，在兼容性优先场景推荐 Chromium。Moli 的真实任务成功率接近或对齐 Chrome/Chromium 后，才讨论默认值。不建议遇错后静默切换，因为登录态、页面状态和操作幂等性通常无法无损迁移。
05 · Integration design

具体应如何集成到 CowAgent

A. 本地 Moli：先利用 CDP，再补官方级启动体验

零代码路径已经可用：用户手动启动 Moli，将现有 tools.browser.cdp_endpoint 指向它。官方集成不应止步于文档，而应新增 engine: moli，负责查找二进制、启动端口、健康检查、profile 目录和退出回收。

"browser": {
  "engine": "moli",             // builtin | system | moli | lexmount
  "moli_path": "/optional/path/moli",
  "moli_layout": true,
  "headless": true
}

代码改动集中在浏览器环境检测/安装与服务创建层，不修改 navigate、snapshot、click、fill 等工具 schema。这是上游容易审阅的边界：新增引擎，不重写 Browser Tool。

B. Lexmount WebFetch：只接管网页分支

在现有 web_fetch 增加 provider = local | lexmount。PDF、Word、Excel 等文件继续使用 CowAgent 当前解析器；HTML/动态网页才进入 Lexmount。URL 在发送到供应商之前继续执行 CowAgent 的 SSRF 与私网地址校验，返回值统一成现有 ToolResult。Lexmount 公开文档当前将 WebFetch API 标注为内测，正式合入前需先确认对外 SLA、配额和版本承诺。

if is_document_url(url):
    return await local_document_fetch(url)
assert_public_url(url)                     # 在任何外部请求之前
if provider == "lexmount":
    result = await lexmount.post("/v1/extract", {
        "extract": {"url": url}
    })  # X-API-Key + X-Project-Id
    return ToolResult(text=result.main_text, metadata={
        "url": result.final_url, "title": result.title,
        "provider": "lexmount", "engine": result.engine,
        "dom_id": result.dom_id
    })
return await local_web_fetch(url)

实现已补齐超时、最大响应长度、最终地址二次校验、状态码映射和凭证脱敏；默认仍为 local，用户显式选择 Lexmount，防止每次读取都产生云费用。自动升级与自动降级暂不加入首版，因为它会使成本和结果来源变得不可预测。

C. Lexmount Cloud Browser：建立 Provider 生命周期，而非硬编码 Endpoint

实现窄接口 BrowserProvider.start() / close()，返回 cdp_endpoint、inspect_url 与 session id；随后仍调用现有 connect_over_cdp。

"browser": {
  "engine": "lexmount",
  "lexmount": {
    "browser": "moli",          // moli | chromium
    "layout": true,
    "resource": false,
    "recording": false
  }
}
  • SDK 按 Python 版本约束安装、运行时懒加载；未选择 Lexmount 时不创建远程会话。
  • 启动失败、工具关闭和空闲回收路径均关闭 Provider 会话，避免孤儿会话计费。
  • CDP 日志只保留 host/port，不输出 path、query token 或完整连接地址。
  • 共享 BrowserService 的复用 key 已加入完整配置与 workspace 摘要，配置变化时先关闭旧会话。
  • Inspect/View URL 仅保存在 Provider 连接元数据中，不进入模型输出。
06 · Upstream landscape

在审 PR 与 Lexmount 的差别：有机会，但要选对赛道

方案它在增加什么完成度与 Lexmount 的关系
PR #3071 · Serply第五个 SERP / Web Search API后端与英文文档；无专门测试、Web UI 与多语言同步；仍在审不直接竞争。Serply 返回搜索结果；Lexmount 提供页面提取和浏览器运行时。
PR #3083 · AnySearch第五个 SERP / Web Search API后端、Web UI、三语文档、178 行测试及手工截图；仍在审不直接竞争，但展示了供应商 PR 的质量门槛正在提高。
Lexmount fork PR #1Moli 本地 Provider、Lexmount WebFetch、Cloud Browser 双内核Provider adapter、配置、三语文档、相关单元/安全测试与真实 smoke 已完成；四个隔离 Web 实例可体验补足 Fetch 与 Browser 运行层，不需要争夺拥挤的 Search Provider 位置。

是否还有机会：有。两个 PR 只扩充搜索供应商，没有解决低资源本地浏览器、动态提取或托管会话。CowAgent 当前又已经支持 CDP，因此 Lexmount 的技术侵入小于新增一套 Browser 动作。不过，“协议可连”不等于“官方必收”：供应商中立性、可维护性、测试覆盖、可选依赖、免费可复现路径和安全边界决定接受概率。

提高接受概率

  • Moli 本地可免费复现，不要求审阅者持有商业账号
  • 先提交引擎抽象与 Moli，商业 Cloud 作为独立后续 PR
  • 保持现有工具 schema 和默认行为不变
  • 带跨平台启动、CDP 合同、SSRF 与日志脱敏测试

降低接受概率

  • 把 Lexmount 包装成不存在的 Search Provider
  • 一个 PR 同时塞入 Search、Fetch、Browser 与控制台大改
  • 默认把全部用户切到 Moli
  • 要求 API Key 才能运行 CI，或在日志泄露连接凭证
07 · Objective assessment

为什么使用，以及为什么不使用

采用 Lexmount 的理由

  • 资源效率：Moli 对 DOM 类任务能显著降低内存、线程和进程数量，提升并发密度。
  • 同一 CDP 动作面：CowAgent 既有 Playwright 动作基本可复用，迁移成本低。
  • 本地到云的连续体验：本地 Moli 免费验证；生产可在 Cloud Moli 与 Chromium 间选择。
  • 基础设施完整：云端会话、代理、观察/接管与生命周期管理是本地浏览器缺少的生产能力。
  • 与 Search 互补：可服务现有搜索供应商，也可承接 CowAgent 搜索后的页面访问。

不采用或暂缓的理由

  • 兼容性边界：未知网站、图形与媒体任务仍以 Chromium 更稳。
  • 云成本与锁定：个人轻量任务用现有本地 Chrome 已足够，接云会增加费用与供应商依赖。
  • 数据边界：云浏览器处理 cookies、页面数据和企业凭证，需要明确地域、保留、审计与删除策略。
  • 能力不对称：Cloud Moli 与 Chromium 在 Context、录制、下载等方面不同。
  • 上游维护成本：新 engine/provider 会扩展 CowAgent 测试矩阵，必须有持续维护承诺。
08 · Two-week delivery

两周可交付范围

两周内可以完成“可运行集成 + 代表性评测 + 可评审材料”，但不能承诺 CowAgent 官方在两周内完成 review 或 merge。当前 fork 的三条能力已在一个 PR 中落地；提交官方上游时，再根据维护者反馈决定保持单 PR 还是按免费 Moli 与商业 Provider 拆分。

已完成 · 三条路径

实现Moli 本地启动/回收、Cloud 双内核 Session、WebFetch 输出归一和本地文档解析保留。
验证真实 Moli 动作合同、相关单元/安全测试、Cloud 凭证链路与 CowAgent + LiteLLM 真实 smoke。
交付fork PR #1、三语文档、四个隔离 Web 实例及可复现浏览器评测。

剩余两周 · 收敛与上游

D1–D3定位 Moli 在 4 个动态生成控件任务中的 click/visibility 超时，形成最小复现并区分内核问题、时序问题与工具适配问题。
D4–D6修复后重跑固定 15 个带 ground truth 的任务；每内核首次执行 1 次，仅失败时最多重试 1 次，并保持暖浏览器与任务间状态清理。
D7–D8补 Cloud Chromium / Cloud Moli 的端到端任务样本与 token、重试和云成本统计。
D9–D10冻结复现材料；按维护者反馈将免费 Moli 与商业 Provider 拆分或收敛提交。

验收标准

  • 不配置 Lexmount 时，CowAgent 默认 Provider 和运行行为不变；当前 fork 安装包会增加按 Python 版本约束的 Lexmount SDK。
  • Moli 覆盖 CowAgent 全部现有 Browser action；不支持项返回明确错误而非假成功。
  • Cloud session 在成功、超时、取消、异常四种路径均自动回收，日志不含 API Key / 完整连接 URL。
  • WebFetch 保留原文档解析，动态网页结果可追溯最终 URL、标题、provider 与渲染状态。
  • 公开区分“实测”“供应商基准”“尚未验证”，不把性能优势外推成通用兼容性。
09 · Recommendation

建议决策

建议推进。首要上游目标是 Moli 本地引擎：免费、可复现、与 CowAgent 现有 CDP 架构对齐，且已经通过原生动作合同实测。Lexmount Cloud Browser 与 WebFetch 同期完成可运行分支和演示，但根据维护者反馈拆分提交，避免商业供应商代码绑架核心浏览器抽象。
  1. 不做 Lexmount Web Search Provider。四家已经真实集成；Lexmount 没有搜索服务。对它们的基础设施合作走商务与后端供给，不污染 CowAgent 的搜索配置。
  2. 把 Moli 定位为并列 Browser Provider。速度和成本优先时推荐 Moli，兼容性优先时推荐 Chromium；真实任务成功率接近或对齐后再讨论默认值。
  3. 云端突出“双内核 + 生产控制”。Cloud Moli 卖密度，Cloud Chromium 卖兼容，二者共同卖会话、代理、可观测、接管和运维。
  4. 官方接受策略以中立抽象为先。先让 CowAgent 获得通用 Browser / Fetch Provider 接缝，再把 Lexmount 做成其中一个可选实现。

代码结论更新至 2026-09-01 的 CowAgent 集成提交。最新微基准包含 15 个确定性任务（简单、中等、复杂各 5 个），每内核首次执行 1 次，仅结果失败时最多重试 1 次；唯一结果 ground truth 是主指标，固定参考路径完整执行是独立辅指标，不使用 LLM-as-a-Judge。详见《Chromium 与 Moli 浏览器工具调用评测》。本轮 Chromium 结果正确 15/15；Moli 11/15，4 个失败任务重试后均未恢复。资源比较严格排除失败与重试，只使用双方首次结果均正确的 11 个同任务：逐任务 Moli/Chromium 耗时比值 P50/mean/P95 为 0.38×/0.50×/0.93×，CPU 时间为 0.47×/0.55×/1.18×，时间加权平均内存为 0.20×/0.20×/0.28×。这说明 Moli 在成功交集内显著省内存且多数任务更快，但该交集排除了 Moli 失败的复杂动态控件任务，存在选择偏差，不能外推为全部任务普遍更快；动态生成控件的点击成功率也尚未对齐。因此当前证据支持把 Moli 作为兼容任务上的低内存、高速度推荐项，不支持设为默认值。Cloud 与本地链路已使用真实凭证和 gpt-5.6-sol（low）验证；正式商业材料仍应附固定版本、机器配置与可复现脚本。外部 PR 状态可能在报告发布后变化。
